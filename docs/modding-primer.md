## 1. 铁律 (违反 = 返工)

1. **不靠记忆, 只靠查实。** 游戏的键位、枚举值、API 行为、UI 里玩家能改什么,
   全部去反编译/官方文档/实跑里确认。凭印象填的东西**一定**会错, 而且错得很隐蔽
   (踩过: "数字键2=弓箭手"是默认布局, 玩家能在部署界面改; 结果海外用户报
   "弓箭手和骑兵指令反了", 查了三层才定位)。

2. **编译通过 ≠ 能跑; 单测通过 ≠ 能跑。** 交付前必须亲自跑一次真实入口, 看它走到
   正常状态。音频/GPU/权限/文件锁这类问题只在真实运行时暴露, 而且可能只在特定
   时机(如 `start()` 而非 `open()`)暴露。

3. **版本绝不说谎。** 每次部署自增版本号, 且版本号只有一个出处(一个常量文件),
   模组显示名带上它。部署完主动向用户报版本号, 让他在游戏里能核对自己装的是哪版。
   没有这条, "我改了你没生效"会浪费掉整个下午。

4. **别按名字猜行为。** 要用引擎的某个类/行为/状态机, 先反编译看它的生命周期方法
   实际干了什么。名字叫 `ProtectFlank` 的行为可能顺手把你的编队合并了。

5. **改动要可回滚、可开关。** 任何影响核心链路的新机制都配一个配置开关
   (默认开, 出问题让用户一行配置关掉), 不要逼用户等下一版。

6. **给"找不到/为空"的分支单独想一遍。** 游戏代码里这类兜底经常是**扩大作用域**
   而不是报错 —— 这是模组里最常见的灾难性 bug 源。
   (血案: 按一个没有部队的编队号, 游戏的兜底是"选中全军"; 于是队里没骑兵时,
   一句误听的"骑兵冲锋"变成全军冲锋。)

## 2. 方法论: 先反编译, 再动手

### 拿到游戏的真实代码

C#/Unity/.NET 游戏(骑砍2、大多数 Unity 游戏)用 ILSpy 命令行:

```bash
dotnet tool install -g ilspycmd
# 单个类型(最常用, 输出小)
ilspycmd -t <完整命名空间.类名> <游戏DLL> | less
# 整个 DLL 反编译成源码树, 然后 grep
ilspycmd -p -o /tmp/src <游戏DLL>
```

找不到完整命名空间时, 直接在 DLL 二进制里捞字符串:

```bash
grep -ao "TaleWorlds\.[A-Za-z.]*" Game.dll | sort -u | head -40   # 命名空间清单
grep -ao "SelectFormation[A-Za-z0-9]*" *.dll | sort -u            # 找方法/类名
```

其它引擎: Unity(IL2CPP) 用 Il2CppDumper + Ghidra; Unity(Mono) 同上 ILSpy;
虚幻用 UE4SS / FModel; 原生 C++ 只能 Ghidra/IDA + 社区逆向文档。

### 查一个行为的标准流程(照着做能省半天)

1. 从**用户看得到的入口**倒推: 玩家按的那个键 → 哪个 InputHandler → 哪个 VM →
   哪个 Controller → 最终改了什么状态。一层层反编译, 别跳步。
2. 到了关键分支, **把 `else` 和 `null` 那条路也读完**(见铁律 6)。
3. 把结论**连代码片段一起**写进项目文档, 注明查证日期和游戏版本 —— 下次别人
   (或换了上下文的你)不用重查。
4. 枚举值、槽位号这类"数字含义", 一定确认它是**语义**还是**索引**。
   索引背后的语义是可变的。

### 引用游戏 DLL 编译 = 免费的 API 兼容性检查

模组项目直接引用**本机游戏安装目录里**的 DLL(别把 DLL 提交进仓库, 也别写死路径):

```xml
<Reference Include="TaleWorlds.MountAndBlade">
  <HintPath>$(BannerlordDir)\bin\Win64_Shipping_Client\TaleWorlds.MountAndBlade.dll</HintPath>
  <Private>false</Private>   <!-- 不要拷贝到输出目录 -->
</Reference>
```

这样"编译通过"就等于"这些 API 在这个游戏版本上存在", 游戏更新后重编译立刻知道
哪里断了。游戏目录要靠**探测**定位(环境变量 → 各 Steam 库常见位置 → 报错提示),
写死路径的代价是用户移一次 Steam 库就全链路崩。

## 3. 在游戏进程里怎么调试

模组跑在游戏进程里, 没有断点、没有控制台、崩了就是游戏崩了。所以:

- **一上手就做日志**。往一个固定文件追加写(带时间戳), 每个关键分支打一行
  ("我进到这个函数了 / 我拿到的对象是 null / 我决定走 A 分支")。
  这类"信标日志"是唯一能回答"为什么没反应"的东西。
- **心跳行**。每隔几秒写一行"我还活着 + 当前状态", 用来区分"模组没加载"、
  "模组加载了但没进战斗"、"进了但拿不到对象"三种完全不同的故障。
- **游戏内可见的回执**。把"我收到了什么指令、对谁执行了"直接显示在游戏 UI 上
  (横幅/消息区)。玩家和你都能一眼看到, 比事后读日志快一个数量级。
- **异常一律吞掉但记下来**。模组里任何一个未捕获异常都可能弄崩别人的存档。
  `try { ... } catch (Exception e) { Log(e); }`, 宁可功能失效不要游戏崩。
- **反射调私有 API 要包容错**。游戏更新会改私有成员, 反射失败必须优雅降级。

## 4. 模组 ↔ 外部程序 (如果要做伴侣程序)

游戏内模组能力强但环境受限(不能开窗口、不能用任意库); 外部程序反之。组合起来很香,
但接缝处有几个坑:

- **通信用本机 TCP + 单行文本协议**(一行一条命令, UTF-8), 不要上 gRPC/共享内存。
  纯文本协议能用 telnet/脚本手工发一行来排错, 这个价值远超性能差异。
- **模组只在需要时监听**, 例如只在战斗中开端口。外部程序"连不上"本身就是有用信号
  (= 不在战斗)。
- **外部程序必须能在没有模组时工作**(降级到模拟按键之类), 模组是增强不是依赖。
  反过来也一样: 模组不能假设外部程序在。
- **谁先启动是不确定的。** 需要同步的配置(比如语言)走**文件**而不是协议 ——
  文件没有时序问题, 协议有。
- **所有请求在游戏主线程执行。** socket 线程只把请求塞队列, 在游戏的 tick 里出队
  处理再回复。在 socket 线程上直接碰游戏对象 = 随机崩。
- **回复要能自解释**: `ok <细节>` / `err <原因码>`。外部程序据此决定降级路径,
  原因码也直接进日志。
- **协议格式两侧各写一份, 必然漂移。** 用一个测试把线格式钉住(起一个真 socket,
  喂一条手抄的真实回复, 断言外部程序解析出正确结果)。

## 5. 交付与验证

- **真实入口自测**, 见铁律 2。给用户之前至少完整启动一次。
- **测试分层**: 纯逻辑做单测(秒级, 每次都跑); 涉及游戏对象的只能实测。
  把"只能实测"的部分列成一张清单交给用户, 每条写明**怎么造出那个场景**
  (例: "带一支没有骑兵的队伍进战斗, 喊骑兵冲锋, 应该只提示不发键")。
- **用例的单一出处**。测试用例写在一个表里, 改表会挪题号, 所以缓存/录音等产物
  按**内容哈希**命名, 绝不按题号 —— 否则改一次表全部对不上。
- **回归锁定**。每修一个 bug 就加一条断言把它钉死, 注释里写清楚"这条是为了防什么"。
  没有这句注释, 半年后有人会"顺手简化掉"它。
- **模拟新用户**。做一个脚本把用户数据目录/缓存**改名藏起来**(可逆, 绝不删),
  跑完再还原。首次跑这个脚本通常立刻抓到一类 bug: 成品在开发机上能跑, 是因为
  开发机有一堆新用户没有的东西。
- **UI 改动后扫元素重合 + 文案截断**。i18n 永不写死字符宽(中英宽度差 30~100%)。
- **AI 工具环境测不了的东西要认**: 全局热键、麦克风、GPU、窗口焦点。这些只能交给
  用户实测, 该说清楚, 不要假装验证过。

## 6. 分发与用户支持

### Steam 创意工坊

- **内容没变的上传是空操作**: 文件没改的话 changenote 会被忽略、更新时间不动。
  改说明/改日志得去网页后台, 命令行改不动。
- **订阅了但启动器里看不到** 是最高频的求助。真相通常是 Steam 还没下完 ——
  启动器只列出"已安装成功"的工坊项, 没下完的**静默不显示**, 没有任何提示。
  这条要直接写进模组简介的 FAQ, 能省掉一半评论区答疑。
- **模组元数据 XML 解析失败会弹错误框**, 玩家只看到一个看不懂的 ERROR。发版前
  必须校验 XML。
- 包体越大, 上面两个问题越严重。认真考虑资源按需下载而不是全打进包。

### 用户支持

- **做一个"打包日志"按钮**: 一键把所有日志压成 zip 给用户去发。要写明"不含隐私
  内容"并且**真的不含** —— 不放音频、不放识别文本、不放设备名。
- **无日志也要能排查**: 提前想好"用户说不行但给不出任何信息"时, 你靠什么区分
  几种可能。通常答案是"模组内心跳 + 游戏内可见回执"(见第 3 节)。
- **PyInstaller / 自解压程序会被杀毒误报**, 提前在简介里说明, 别等用户骂。
- 需要联网下载资源时, **在你自己的网络里测不出别人的网络问题**。做一个"体检脚本"
  定期从目标地区的探针(有免费的公共探针 API)测可达性, 并在代码里实现
  多源测速择优 + 断点续传 + 卡住换源 + 校验和。
  最坑的不是"连不上"(会抛异常), 是"连得上但极慢/卡死不抛错"。

## 7. 在 AI 工具环境 (Claude Code 等) 里干活的特殊坑

- **看到的 `%LOCALAPPDATA%` 可能是假的。** Claude 桌面版是 MSIX 包, 它拉起的
  终端/python 对 AppData 的写入会被**重定向**到
  `%LOCALAPPDATA%\Packages\<包名>\LocalCache\Local\`, 读取是"影子层 + 真实目录"
  的合并视图, 同名文件影子层优先。后果: 从工具里改配置/改数据目录, 容器外的成品
  看不见; 之后读日志读到的是影子层的旧文件。
  **规矩: 工具里对用户数据目录只读不写**; 必须写就走容器外进程
  (如 WMI `Win32_Process.Create` 起的进程没有包身份)。读到的时间戳对不上时,
  先 `realpath` 看是不是影子层。
- **全局键盘钩子收不到任何事件**(容器内进程、以及 session 0 无桌面的进程都一样),
  连自己发的键都收不到。热键逻辑只能靠假键盘对象做单测, 真按键交用户实测。
- **heredoc 容易吃掉转义**。往文件里写含 `\n`、引号、中文的内容时, 用文件写入工具
  而不是 shell heredoc; 非要用脚本就先断言"要替换的原文出现次数 == 1" 再替换。
- **注意行尾**。仓库里可能是 LF 而工作区是 CRLF。用脚本改文件前先探测文件自己的
  行尾并沿用, 否则一次改动会产出整文件的假 diff, 把真实改动埋掉。
- **别提交用户的本机配置**。配置文件里常混着用户的设备名/语言/路径。只暂存自己
  那几行(必要时用 `git hash-object -w` + `git update-index` 手工构造要提交的版本)。
- **多会话并行用 git worktree**: 每个方向一个 worktree + 一个会话, 跨会话的共识
  写进仓库里的文档(而不是某个会话的记忆), 否则另一边永远掉队。

## 8. 附录: 骑砍2 (Bannerlord) 专用速查

> 换游戏就跳过本节。保留是因为下一个模组很可能还是骑砍。

- **目标框架 net472**, 引用 `<游戏>/bin/Win64_Shipping_Client/TaleWorlds.*.dll`
  和 `<游戏>/Modules/<模块>/bin/.../*.dll`。产物放
  `Modules/<你的模组>/bin/Win64_Shipping_Client/`, 配一个 `SubModule.xml`。
- **入口**: `MBSubModuleBase`(模块级) + `MissionBehavior`(战斗级, 每场战斗一个实例,
  `OnBehaviorInitialize` / `OnMissionTick` / `OnEndMission`)。
- **编队 (Formation) 的两个"类"要分清**:
  - `Formation.Index` == `(int)FormationClass` —— **槽位号**, 也是玩家按的数字键 -1。
  - `Formation.LogicalClass` —— 玩家在"战斗部署 Order of Battle"里给这个槽**指定**的兵种。
  - `Formation.PhysicalClass`(= `QuerySystem.MainClass`) —— 槽里**实际**占比最高的兵种。
  - `GetCountOfUnitsBelongingToPhysicalClass(cls, false)` —— 逐个数 agent 的精确人数。
  **要"哪支队是骑兵"就用实际成分数人数**, 不要用槽位号。`QuerySystem` 的各种
  `Is*Formation` / 比值有 2.5~15 秒缓存, 要即时值用非 `ReadOnly` 的那个属性。
- **选队**: `Mission.Current.PlayerTeam.PlayerOrderController` 上的
  `ClearSelectedFormations()` / `SelectFormation(f)` / `SelectedFormations` /
  `IsFormationSelectable(f)`。模组这样选队 UI 会同步(`MissionOrderVM.OrderController`
  就是同一个对象, 且 troop controller 订阅了 `OnSelectedFormationsChanged`)。
  选一个活人为 0 的编队会触发 `Debug.FailedAssert`, 先用 `IsFormationSelectable` 挡。
- **数字键的真实语义**: `GauntletOrderUIHandler` 里 GameKey 78 = 选全军,
  79~86 = 槽 0~7; 落到 `MissionOrderTroopControllerVM.OnSelectFormationWithIndex`,
  **该槽没有部队时走 `else SelectAllFormations()`** —— 缺兵种时按键 = 全军令。
- **绝不 `SetControlledByAI(true)`**。一交 AI, 团队 AI 的战术层就接管该编队
  (合并步弓、圆阵套方阵、给骑兵派 ProtectFlank), 你挂的特殊行为赢不了权重竞争,
  玩家还改不回来。正解是**影子驱动**: 反射调一次 `OnBehaviorActivatedAux` 激活,
  然后每 0.5s 自己调该行为的 `TickOccasionally`(让它自己下移动/朝向令), 编队全程
  留在玩家手里; 监听 `OrderController.OnOrderIssued`, 玩家一下直接指令就停驱动。
- **挑行为类之前反编译看 `OnBehaviorActivatedAux` / `TickOccasionally` 到底干什么**,
  别按类名猜。
- **游戏内通知双通道**: `MBInformationManager.AddQuickInformation`(顶部横幅, 显眼)
  + `InformationManager.DisplayMessage`(左下战斗记录, 可回翻)。两个都发。
- **启动器只列出 `SteamUGC.GetItemInstallInfo` 成功的工坊项** —— 没下完的模组
  在 Mods 页**静默消失**, 这是"订阅了却看不到"的根因。
- `ModuleHelper.GetPhysicalModules` / `GetPlatformModules` 在模组 XML 解析失败时
  会弹**可见的 ERROR 对话框**; `ModuleInfo` 的 `Category` 默认 `Singleplayer`。

## 9. 开工清单 (第一天就做掉)

- [ ] 定位游戏目录的**探测**函数(环境变量 → 常见路径 → 明确报错), 不写死路径
- [ ] 引用本机游戏 DLL 的编译能过(= API 兼容性检查到位)
- [ ] 版本号单一出处 + 模组显示名带版本 + 部署脚本最后打印版本号
- [ ] 信标日志 + 心跳 + 游戏内可见回执, 三件套先搭好
- [ ] 一键部署脚本(编译 → 组装 → 体检 → 报版本), 部署前检查游戏是否在运行
- [ ] 一键"打包日志"给用户用
- [ ] 秒级单测套件 + 一条命令跑全部
- [ ] "模拟新用户"脚本(藏起数据目录, 可逆不删)
- [ ] 项目 `CLAUDE.md`: 架构一图流 / 铁律 / 已查实的游戏内部事实(带日期和游戏版本)
      / 只能实测的清单
